Fly-in, explained like you're new here

What does this project actually do?

Picture a busy airport. A bunch of delivery drones all need to fly from the same starting gate to the same finish line, but they share hallways and rooms that can only fit so many drones at once. This project is the "air traffic control" brain: code that decides, one step at a time, who goes where — so nobody crashes, nobody gets stuck, and everybody arrives as fast as possible. This page explains, in plain words, how every piece of that code works.

01

How a map file turns into a flight plan

Here's the big trick: the computer does NOT figure things out turn by turn while you watch. It plans the whole trip, for everyone, before the first turn even happens — then it just reads that plan out loud.

Think of it like a relay race with a coach who plans every runner's leg on paper first, then just calls out the plan as the race happens. Below are the six steps the code goes through, in order, to turn a text file into a finished schedule. Each step does one job and hands a finished result to the next step — nothing gets redone or guessed twice.

02

The four building blocks

Everything in this project is built from four simple ideas. Once you know these four, the rest of the code is just details.

A zone is a place — like a room. A connection is a road between two zones. A drone is, well, a drone. And a graph is just the whole map: every zone and every connection, bundled together. Zones also come in four flavors, and the flavor decides how long it takes to enter one:

normal · a plain room, 1 turn priority · a nice shortcut, still 1 turn restricted · slow, takes 2 turns blocked · a locked door, never enter

src/zone.py · Zone

A room. It keeps its own little guestbook of who's inside, turn by turn.

def has_room_at(self, turn: int) -> bool:
    return (
        self.has_unlimited_capacity
        or self.occupancy_at(turn) < self.max_drones
    )

def reserve(self, turn: int, delta: int = 1) -> None:
    self._reservations[turn] += delta
  • In plain words: "is there room for one more, on this turn?" and "add (or remove) one drone from this turn's headcount."
  • The room only counts how many drones are inside, never which ones — like a parking garage counting cars, not license plates.
  • The start room and the finish room are special: they never fill up. Any number of drones can be there at once.

src/connection.py · Connection

A road between two rooms. It has the exact same kind of guestbook.

def other(self, zone_name: str) -> str:
    return self.zone_b if zone_name == self.zone_a else self.zone_a

def has_room_at(self, turn: int) -> bool:
    return self.occupancy_at(turn) < self.max_link_capacity
  • Works exactly like a room, just for a road: "how many drones are crossing me right now?"
  • A road's name is always exactly what the map file called it (like "gate1-gate2") — so it's printed correctly later.

src/drone.py · Drone

Just a name tag and a plan. The drone doesn't "think" for itself.

Event = Tuple[int, str, str]  # (turn, "zone"|"conn", name)

def location_before(self, turn: int) -> Optional[Event]:
    best: Optional[Event] = None
    for event in self.timeline:
        if event[0] > turn:
            break
        best = event
    return best
  • All the smart decisions happen once, ahead of time. The drone just follows its plan like a script — it never has to "decide" anything mid-flight.
  • You can always ask a drone "where will you be on turn 7?" — that's what this code answers.

src/graph.py · Graph

The whole map, bundled together: every room, every road, plus which one is home base.

def add_connection(self, connection: Connection) -> None:
    self.connections.append(connection)
    self._adjacency[connection.zone_a][connection.zone_b] = connection
    self._adjacency[connection.zone_b][connection.zone_a] = connection
    self._by_name[connection.name] = connection
  • It's like a phone book for the map: give it two room names, it tells you if there's a road between them.
  • It also remembers which room is the start and which is the finish, so nothing else has to go looking for them.
03

How the map file gets read

The computer reads the map text from top to bottom, just once — like reading a recipe before cooking, not re-reading it every five seconds.

First line: how many drones there are. Then: every room. Then: every road. Nothing is stored in some in-between, temporary format — the moment a line checks out, it becomes a real Zone or Connection, ready to use. And if anything doesn't make sense — a typo, a room mentioned twice, a road to a room that doesn't exist — the program stops right there and says exactly which line is wrong.

src/parser.py
pair = frozenset((zoneA, zoneB))
if pair in self._connected_pairs:
    raise ValueError(
        f"Duplicate connection '{zoneA}-{zoneB}'. "
        "This path already exists."
    )
self._connected_pairs.add(pair)

declared_name = match.group(1)
self.connections[declared_name] = Connection(
    zone_a=zoneA, zone_b=zoneB,
    max_link_capacity=capacity, name=declared_name,
)
  • Same road, written backwards, still counts as a duplicate: if the map lists gate1-gate2 and later gate2-gate1, this code catches it — those are the same road.
  • Names are kept exactly as written: if the map calls a road corridorA-tunnelB, that is exactly what gets printed later — never a different spelling.
  • Stop immediately on any mistake, and say exactly which line caused it — no silent guessing.

Once every line has been checked, putting it all together into "the map" is the easy part — just a few lines that hand everything already built over to the Graph: 

def build_graph(self) -> Graph:
    graph = Graph()
    graph.nb_drones = self.nb_drones
    for zone in self.zones.values():
        graph.add_zone(zone)
    for connection in self.connections.values():
        graph.add_connection(connection)
    return graph
04

The brain: how a route gets planned

This is the cleverest part of the whole project — a mini GPS, built completely from scratch, for many drones at once.

A normal GPS asks: "what room is the drone in?" This one asks a smarter question: "what room is the drone in, AND what turn is it?" That one small change is basically the whole secret. Because now, the computer simply never lets two drones be told to be in the exact same room on the exact same turn. No crashes, ever — not because anyone checks for them, but because the plan can't even be written that way in the first place.

Every drone only ever has 3 choices

At every single turn, a drone can do exactly one of three things: wait where it is, move into a normal (or nice-shortcut) room, or start crossing into a slow room. One small piece of code checks all three, and only allows a move if there's actually room for it:

src/pathfinder.py — the "what can I do next?" check
zone = self.graph.zones[zone_name]
if zone.has_room_at(turn + 1):
    consider(zone_name, turn, zone_name, turn + 1,
             priority_score, [(turn + 1, "zone", zone_name)])

for neighbor in self.graph.neighbors(zone_name):
    if neighbor.zone_type == ZoneType.BLOCKED:
        continue
    connection = self.graph.connection_between(zone_name, neighbor.name)
    bonus = -1 if neighbor.zone_type == ZoneType.PRIORITY else 0

    if neighbor.zone_type == ZoneType.RESTRICTED:
        arrival = turn + 2
        if (connection.has_room_at(turn + 1)
                and connection.has_room_at(turn + 2)
                and neighbor.has_room_at(arrival)):
            consider(zone_name, turn, neighbor.name, arrival,
                     priority_score + bonus,
                     [(turn + 1, "conn", connection.name),
                      (turn + 2, "conn", connection.name),
                      (arrival, "zone", neighbor.name)])
    else:
        arrival = turn + 1
        if connection.has_room_at(arrival) and neighbor.has_room_at(arrival):
            consider(zone_name, turn, neighbor.name, arrival,
                     priority_score + bonus,
                     [(arrival, "conn", connection.name),
                      (arrival, "zone", neighbor.name)])

Don't worry about reading every line — the important part is the three checks: "is there room to just wait here?", "is the next room free?", and if it's a slow room, "is there room for BOTH turns of the crossing?". This is the only place in the whole project that creates a slow-room crossing, and it always reserves both turns at once. That's exactly why a drone can never get stuck half-way through a crossing — that situation was never allowed to exist in the first place.

Making the plan faster

The first plan the computer makes — routing drones one at a time — usually works, but it's rarely the fastest possible plan. So afterward, the computer plays a little game with itself, up to 500 times: pick one or two drones at random, erase their plan, and look for a quicker one. If the new plan gets everyone done sooner (or at least not slower), keep it. If not, throw it away and try something else.

src/pathfinder.py — the "keep it or undo it?" check
if candidate_makespan <= best_makespan:
    for index, new_path in replanned.items():
        paths[index] = new_path
    if candidate_makespan < best_makespan:
        best_makespan = candidate_makespan
        best_paths = [path[:] for path in paths]
        no_improvement = 0
    else:
        no_improvement += 1
else:
    # revert: put the old reservations back
    ...
    no_improvement += 1
  • It's even allowed to try a "sideways" swap — same speed, different plan — because sometimes that opens the door to a better idea a few tries later.
  • If 100 tries in a row don't help, it stops trying — no point running forever.
  • "Undoing" a bad idea is easy, because every room and road already keeps its own guestbook — undoing just means erasing those entries again.
05

Playing the plan out, turn by turn

Once the plan exists, "running the simulation" is really just reading it out loud, one turn at a time.

There's one tricky little bit, though: telling apart "a drone really moved" from "a drone just waited in place." The rules say a waiting drone should not be listed for that turn. So the code checks a simple question: is the drone in the same room it was already in? If yes, it just waited — skip it. If no, it's a real move — print it.

src/simulation.py — "did it really move, or just wait?"
if zone_event is not None:
    if zone_event == self._zone_before(drone, turn):
        return None  # same zone as before → it waited, omit it
    return zone_event
return conn_event  # only a "conn" event → mid-transit, show the link

the official answer

One plain line per turn. No colors, no extra words — just the moves.

  • Always looks like D1-roomName or D2-roadName, one line per turn, exactly as the assignment asks for.
  • Once a drone reaches the finish room, it just stops showing up — no special "mark as done" code needed, it falls out naturally.

the human-friendly version

A colorful printout, just for people watching in a terminal — kept completely separate from the official answer.

  • Shows the same moves in color, plus a quick snapshot of which drones are in which room right now.
  • Colors come from the map file itself if it set one, or a sensible default color for that type of room otherwise.
src/colors.py
def zone_color(zone: Zone) -> str:
    if zone.color:
        return NAMED_COLORS.get(zone.color.lower(), TYPE_COLORS[zone.zone_type])
    return TYPE_COLORS[zone.zone_type]

Eighteen everyday color words (like "red", "sky", "gold") get turned into terminal colors. If a room has no color at all, it just uses a default based on its type — slow rooms are reddish, nice shortcuts are greenish, and so on.

06

Actually running the program

Starting the whole thing only takes four real lines of code; the rest is just reading arguments and handling mistakes nicely.

src/main.py
map_parser = MapParser(args.map_file)
map_parser.parse()
graph = map_parser.build_graph()
Simulation(graph, console=console).run()

In plain words: read the map file, check it, build the map object, then plan and play out every drone's trip. If the map file itself is broken, that's caught while reading it. If a drone simply has no possible way to reach the finish, that gets caught here and reported clearly instead of crashing.
